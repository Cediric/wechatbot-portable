# 微信bot v6.19 验收报告

日期：2026-10-18。依据用户提供的 wechat-bot-log-2026-10-18(1).txt，对照最初用户版 v5.1 和 [Akasha-WeChat 上游](https://github.com/alingalingling/Akasha-WeChat)，本地参考提交为 9dbe933a9f1bc46e33ca8121334bb1dd01173248。上游现有文本、图片发送与会话缓存，不包含本项目的语音、生图和朋友圈；不能把这些新增模块说成已经通过上游验证。

## 连续消息与媒体

日志中“发个语音”后接“然后发个图片”，旧轮语音被新消息取消，而第二句也没被明确图片规则识别。原实现每条输入立即推进回复代次，插件又无条件停止同会话运行，导致正常补充请求也会截断已准备的工作。

本版普通补充消息沿用缓冲，等当前流式回复或语音任务结束后处理；明确停止要求仍能取消。图片识别支持“然后”“顺便”等连续请求语境，引用、转述及否定不触发生成。顺序索要语音再图片时，已准备的图片只在前项交付确认后送出；各出口记录独立结果，图片失败不重发已经成功的语音。原有合成失败时的单次文字后备保留，录音发送结果不确定则停止。没有新增第二套任务队列或程序代写台词。

交叉审查补齐三个具体边界：缓冲要等语音及后续图片的整个发送任务结束；队列拒绝或执行前取消立即释放失败请求；模型无进展按已有模型和发送超时释放，不拿十分钟去重保留期作为等待上限。同一批先索要媒体再取消时，只取消之前的媒体意图，完整聊天证据仍保留给主模型。

## 语音与朋友圈

服务器日志表明语音已合成，但当前录音手势没有被确认；前版整桌面预查导致的长时间等待已不在这次失败里。本版发现右 Alt 开关会压过实际存在的录音按钮，恢复用户初版的严格录音按钮优先、右 Alt 后备顺序，仍在录音确认后播放。听写按钮不当作语音消息入口。没有重加固定三秒等待。

朋友圈只在导航阶段，对同一物理窗口短暂缺失的列表复用现有恢复路径。滚轮前后重新取得当前列表，接受 Qt 正常重建；仍核对当前微信窗口、列表归属、视口及前台。日志中 Chrome 实际占据前台的情况继续停止，不在最终互动前抢回焦点。

定向回复无法选择时，只收起本任务刚打开且仍为空的编辑器，避免下次轮询误当成已有草稿；用户原有草稿及已尝试提交的状态保留。同作者发表多条不同正文的评论，可按原生评论编号与唯一正文匹配；同作者同正文存在多个原生编号时仍不猜选。

## 验证范围

本轮在本地进行有限的相关回归与独立代理交叉审查，核对连续消息、明确取消、媒体顺序、录音入口、列表重建及草稿归属。完整双包另作文件、版本、依赖和私人覆盖层审计，结果记录在包外 final-v6.19-independent-zip-audit.json。

本轮未启动本机项目、操作真实微信、调用付费模型或远控服务器。模拟控件只能验证程序分支与顺序，不能证明服务器录音、图片或朋友圈已经发送成功。生图连接曾有 TLS 提前关闭错误；本轮修复图片请求识别，不将其等同于服务器网络问题已经消失。

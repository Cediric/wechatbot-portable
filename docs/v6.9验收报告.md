# 微信bot v6.9 验收报告

本轮优化响应关键路径并生成完整干净包及自用包。仅在本地执行合成UIA、模拟模型和受控回环HTTP测试，没有操作微信、目标服务器或真实付费API。

## 优化与证据

目标控件扫描保留已知聊天历史容器本身，跳过其无关后代；搜索结果仍动态读取，身份、窗口、前台、编辑器、草稿和代次每次重新核验。同一原生ID匹配、300条历史节点的合成发送场景，属性读取由2586次降到415次，约减少84%；父链读取75次降到63次。发送结束的快照为本次普通数据观测，不再做COM、编辑器发现或全树扫描。独立prepare/diagnostics仍取得完整新鲜视图，面板区分来源和发送处理中状态，不把观测快照用作发送授权。

流式模型读取使用最多4个待发片段的有界队列，与微信发送等待重叠。只有一个发送消费者持有序号、回复禁律和媒体暂存状态；第一句准备好即进入发送，最终空控制按队列顺序发送一次。取消、模型异常或未确认发送会停止剩余片段，取消并等待读取任务，关闭上游生成器，不重新生成或重放已提交内容。边界测试实际验证第一句发送等待期间，后续模型内容已经读到；这主要减少后续读取被界面等待阻塞，不宣称主模型第一句生成更快。缓冲上限为4个待发片段，此外最多1个发送中和1个读取任务等待入队的片段。

上一轮消息处理期间已经等待的合并时间被计入下一轮，只补尚未消耗的私聊/群聊合并窗口。已静置的消息在释放时安排50毫秒调度下限，刚到的消息仍等待剩余0.35/0.7秒窗口；不是50毫秒直接回复。最大等待期限不被重复扣除；媒体未准备好时保持原顺序，持久事件重试仍使用原间隔，关闭智能合并时保留原行为。

上下文预算裁剪从反复统计整段历史改为每条一次统计，准备过程中只复制一次。一个602条历史场景，统计调用从90852次降到602次，本机裁剪约1.305秒降到0.0024秒且保留相同20条记录；另一工具历史场景从60611次降到602次并保留相同32条记录。与实际六点八源码的4000组随机历史、交错系统/工具消息、媒体和Unicode差分全部一致。这是本机预算处理耗时，不是模型服务或微信端总耗时。

已有HTTP传输本身就是线程本地连接池，本轮没有重复重做连接池。受控回环测试确认两次请求复用同一TCP连接，凭证逐请求独立，两工作线程可并行进入服务；付费自动重试仍为零。新增准备完成发请求前、响应头返回后以及空体/流结束处的取消和期限核验。阻塞读取的取消仍需等网络数据或既有读取超时，不宣称即时中断socket。

## 保留的流程

独立拟真/群聊决策仍先运行，主模型仍获得原人设、内置工作流、真实身份与决策结果；图片规划依赖真实拟真计划，未提前生成或删除决策步骤。模型渠道、模型名、思考档位、256k上下文配置、记忆、音色和参考图不变。

0.8秒首回复下限、0.25秒气泡间隔、私聊合并0.35秒和群聊0.7秒设置保留；已有耗时只补剩余下限，不叠加等待。朋友圈150分钟发布决策、240分钟主动浏览及私聊空闲60秒规则不变，六点八的逐条媒体失败隔离和SNS恢复随包保留。

## 回归与交叉检查

- 流式、主消息流程、跨会话媒体、耗时及合并等待144项通过，包含新增6项并行预读/失败/取消边界和7项合并等待用例。
- 原UIA、恢复资料、恢复流程与版本无关发送258项通过，新增5项性能和风险用例通过；另有97项独立交叉重跑包含既有用例，不重复加总。
- 模型、真实回环HTTP、工作流与线程连接24项通过；独立复核重跑18项为上述子集。
- 两个真实面板脚本的合成行为测试通过，包含快照来源、发送中状态、朋友圈媒体错误和未提交原因。
- UIA、模型与流式/消息合并由子代理交叉复核；最终完整双包另行核对CRC、文件清单、源码字节、版本、私人配置及素材隔离和SHA-256。

目标服务器网络、模型服务和微信界面未在本轮实测，不能保证固定首回复秒数。新日志继续区分首内容、完整句准备、模型流读取完成、界面发送与队列耗时，便于之后衡量实际改善。

## 升级

自用配置和素材与已验收六点八逐项保留，两个包包含相同完整公共源码和运行依赖。升级时将旧桥接目录的config.json和data复制到新包同位置，保留已启用开关、账号和记忆；AstrBot实例迁移见[便携说明](../portable/README.md)。新目录不会自动合并旧数据。
